# About / Contact 나무위키형 전환 분석 및 V1 명세

- 상태: 1단계 분석 완료, 구현 미착수
- 작성일: 2026-08-02
- 대상: `about.html`의 About / Contact 통합 문서
- 목적: 나무위키의 핵심 읽기·편집·이력 경험을 개인 홈페이지 규모에 맞게 재구성한다.

## 1. 결론

현재 About은 **나무위키처럼 보이는 한 장짜리 관리자 소개 문서**다. 표, 목차, 번호 섹션, `[편집]` 링크는 있지만 실제 저장과 편집 방식은 위키가 아니다.

V1은 다음 방향으로 만든다.

1. 공개 화면은 지금의 90년대 개인 홈페이지 감성을 유지하면서 위키 문서처럼 읽힌다.
2. 본문 원본은 WYSIWYG HTML이 아니라 사람이 직접 고칠 수 있는 나무마크 계열 원문으로 저장한다.
3. 관리자는 `원문 편집 → 미리보기 → 편집 요약 → 저장` 순서로 수정한다.
4. 저장할 때마다 덮어쓰지 않고 새 리비전을 남긴다.
5. 공개 사용자는 문서를 읽고 이력을 볼 수 있다.
6. 방문자 편집 요청은 V1 핵심이 안정된 뒤 V1.1 선택 확장으로 추가한다.

즉, 목표는 “나무위키 전체 복제”가 아니라 **About 한 문서에 필요한 작은 위키 엔진**이다.

## 3. 현재 About / Contact 구조

### 3.1 사용자가 보는 화면

현재 `about.html`은 다음 순서로 보인다.

1. `김찬수` 문서 제목
2. 프로필 표
3. 목차
4. 번호가 붙은 소개 섹션
5. Contact를 포함한 하위 섹션

로그인한 관리자는 프로필과 각 섹션의 `[편집]`, 섹션 순서 변경, 추가·삭제 기능을 쓴다. 일반 방문자는 완성된 문서만 본다.

### 3.2 실제 편집·저장 방식

- 편집기는 BlockNote 기반 WYSIWYG다.
- 저장 원본은 나무마크가 아니라 HTML이다.
- 문서 전체가 `site_settings.about_wiki_document` 한 개 JSON 값에 저장된다.
- 저장할 때 이전 값은 덮어써진다.
- 리비전, 편집 요약, 차이 비교, 되돌리기, 동시 편집 충돌 검사가 없다.
- 유효한 PocketBase 로그인 사용자는 관리자 편집자로 취급된다.
- 공개 회원가입은 막혀 있어 현재 운영상 실제 편집자는 사이트 소유자 한 명이다.

### 3.3 현재 구조의 좋은 점

- 프로필 표와 왼쪽 사이드바가 같은 프로필 데이터를 공유한다.
- 공개 화면에서 바로 고치는 OWNER MODE 철학과 잘 맞는다.
- 한 문서만 관리하므로 사용법이 단순하다.
- 기존 이미지·영상 삽입과 저장 대기열, 편집 중 자동 새로고침 방지 장치를 재사용할 수 있다.

### 3.4 해결해야 할 문제

- 위키처럼 보이지만 수정 기록을 복원할 수 없다.
- HTML 원본은 나무위키식 문법 학습·복사·수정 경험과 다르다.
- 현재는 제목 변경 시 기존 섹션 ID를 유지하지만, 새 리비전 구조에서도 삭제·재생성·순서 변경과 무관하게 앵커 호환을 보장해야 한다.
- CMS 읽기 오류와 “문서 없음”을 구분하지 않고 기본 문서로 대체할 가능성이 있다.
- HTML 정리 함수가 실질적인 보안 정화를 하지 않아 렌더링 경계를 다시 설계해야 한다.
- 모바일 공개 화면에서 페이지 전체 가로 넘침이 발생한다.

## 4. 나무위키형 작동 방식 분석

### 4.1 읽기

핵심 구조는 다음과 같다.

- 문서 제목과 최근 수정 정보
- 문서 상단 기능: 편집, 토론, 역사
- 본문 앞 목차
- 번호가 붙은 제목 계층
- 각 문단의 부분 편집 진입점
- 표, 주석, 접기, 링크, 미디어가 본문 안에서 함께 렌더링됨
- 역사 화면에서 각 리비전, 편집자, 증감량, 편집 요약을 확인함

About V1에서는 토론과 여러 문서 간 이동 구조를 제외하고, 아래 범위에서 선정한 핵심만 가져온다.

### 4.2 편집

확인된 기본 흐름은 다음과 같다.

1. 전체 문서 또는 특정 문단의 편집을 누른다.
2. 원문 텍스트를 직접 편집한다.
3. 미리보기로 렌더링 결과를 확인한다.
4. 편집 요약을 선택적으로 입력한다.
5. 저장하면 새 리비전이 만들어진다.

역사 화면의 diff는 저장된 리비전끼리 비교하는 기능이다. V1의 저장 전 비교 화면은 나무위키 동일 동작으로 주장하지 않고, 실수 방지를 위한 우리 사이트의 추가 안전장치로 둔다.

### 4.3 문법

나무마크 계열은 제목, 글자 꾸미기, 링크, 목록, 인용, 수평선, 각주, 표, 접기, 이미지·동영상, 매크로, 분류, 이스케이프 등을 지원한다.

모든 문법을 한 번에 구현하면 About 한 문서에 비해 파서와 보안 부담이 지나치게 커진다. V1은 실제 소개 문서 작성에 필요한 부분집합을 명시적으로 지원한다.

### 4.4 역사와 되돌리기

역사 화면의 핵심 정보는 다음과 같다.

- 리비전 번호와 시간
- 편집자 표시
- 글자 수 증감
- 편집 요약
- 원문 보기
- 두 리비전 비교
- 특정 리비전으로 되돌리기

되돌리기도 과거 레코드를 삭제하거나 현재 리비전을 이동시키는 방식이 아니라, 선택한 과거 원문으로 **새 리비전**을 만드는 방식이어야 한다.

### 4.5 편집 요청

ACL에서 요청이 허용된 사용자는 직접 저장 대신 편집 요청을 만들 수 있다. 요청자는 제안 원문과 요약을 제출하고, 권한이 있는 사용자가 검토한 뒤 반영하거나 닫는다.

현재 사이트는 개인 About 문서이며 스팸·개인정보·운영 부담이 있으므로 이 기능은 V1.1 선택 확장으로 둔다. V1에서는 방문자에게 비활성 버튼을 미리 노출하지 않는다.

### 4.6 권한

나무위키 전체 ACL을 복제할 필요는 없다. V1 권한은 제품 역할에 맞게 단순화한다.

| 역할 | 읽기 | 역사·diff | 직접 편집 | 되돌리기 | 편집 요청 | 요청 검토 |
| --- | --- | --- | --- | --- | --- | --- |
| 방문자 | 허용 | 허용 | 불가 | 불가 | V1.1 허용 | 불가 |
| OWNER | 허용 | 허용 | 허용 | 허용 | 허용 | V1.1 허용 |

PocketBase 로그인 여부만 보는 현재 방식 대신, 구현 단계에서는 OWNER 역할을 명시적으로 판별해야 한다.

## 5. 현재와 목표의 차이

| 영역 | 현재 | V1 목표 |
| --- | --- | --- |
| 공개 화면 | 위키풍 한 장 문서 | 최근 수정·역사까지 포함한 실제 위키 문서 |
| 편집기 | WYSIWYG | 나무마크 원문 편집 + 미리보기 |
| 저장 단위 | 단일 JSON 덮어쓰기 | 문서 + 추가 전용 리비전 |
| 편집 요약 | 없음 | 일반 저장은 선택, 되돌리기 사유는 필수 |
| 역사 | 없음 | 공개 리비전 목록 |
| 비교 | 없음 | 두 리비전의 줄 단위 diff |
| 되돌리기 | 없음 | 과거 원문을 새 리비전으로 복원 |
| 충돌 방지 | 없음 | 기준 리비전 검사 후 충돌 안내 |
| 방문자 기여 | 없음 | V1.1 선택 확장: 편집 요청 |
| 모바일 | 페이지 가로 넘침 존재 | 페이지 넘침 없음, 표만 내부 스크롤 |

## 6. V1 범위

- 리비전 역사
- 원문 보기
- 리비전 diff
- 되돌리기
- 낙관적 잠금 기반 동시 편집 충돌 방지

- 나무위키 스킨의 픽셀 단위 복제

### 7.1 렌더링 안전 원칙

- 원문을 브라우저 `innerHTML`에 직접 넣지 않는다.
- 파서 출력은 허용된 요소와 속성만 생성한다.
- `https:`, `http:`, 현재 Contact에 필요한 `mailto:`만 허용하고 `javascript:` 같은 위험한 링크 스킴을 거부한다.
- 외부 링크의 새 창 처리에는 안전한 `rel`을 붙인다.
- 이미지·영상은 기존 미디어 출처 규칙을 따른다.
- 파서 에러가 나도 편집 원문은 잃지 않고 오류 위치를 보여준다.
- 프로필 행의 기존 HTML 링크도 별도의 허용 목록 렌더러로 변환하고 검증한다.

### 7.2 입력 문법 계약

V1은 아래 토큰을 고정한다. 나무마크와 같은 토큰을 쓸 수 있는 곳은 그대로 쓰고, 사이트 고유 기능은 `CWK 확장`으로 분리한다.

| 기능 | 입력 예시 | 호환 방침 |
| --- | --- | --- |
| 제목 | `== 제목 ==`, `=== 하위 제목 ===` | 나무마크식 |
| 굵게 | `'''굵게'''` | 나무마크식 |
| 기울임 | `''기울임''` | 나무마크식 |
| 밑줄 | `__밑줄__` | 나무마크식 |
| 취소선 | `~~취소선~~` | 나무마크식, `--문자--` 별칭은 제외 |
| 외부 링크 | `[[https://example.com|표시 이름]]` | 나무마크식 |
| 같은 문서 이동 | `[[#contact|연락처]]` | 나무마크식 |
| 비순서 목록 | ` * 항목` | 줄 시작 공백을 포함한 나무마크식 |
| 순서 목록 | ` 1. 항목` | 줄 시작 공백을 포함한 나무마크식 |
| 인용 | `> 인용문` | 나무마크식 |
| 수평선 | `----` | 나무마크식 |
| 각주 | `[* 각주 내용]` | 나무마크식 |
| 표 | `|| 셀 1 || 셀 2 ||` | 기본 나무마크식, 셀 병합 제외 |
| 접기 | `{{{#!folding 제목` + 본문 + `}}}` | 나무마크식 |
| 이미지·영상 | `[[파일:media-record-id|설명]]` | CWK 확장: 기존 media 레코드를 참조 |
| 리터럴 | `{{{문법으로 해석하지 않을 내용}}}` | 나무마크식 |

- 토큰의 중첩 우선순위, 줄바꿈, 깨진 닫힘 문자는 fixture 테스트 결과를 계약으로 삼는다.
- HTML 태그는 원문 문법으로 허용하지 않는다.
- 미디어 선택기에서 기존 파일을 고르거나 새 파일을 올리면 편집기 커서 위치에 `[[파일:...]]` 토큰을 삽입한다.
- 이미지·영상의 원본 파일은 기존 정책대로 보존하며, 어떤 공개 또는 억제 리비전에서든 참조 중인 media 레코드는 물리 삭제하지 않는다.
- 섹션의 안정적인 앵커는 제목 직전의 `<!--cwk:section=stable-id-->` 예약 메타 토큰으로 보존한다. 이 토큰은 화면에 렌더링되지 않으며 일반 HTML로 실행되지 않는다.
- 부분 편집에서 제목을 바꿔도 예약 ID를 유지한다. 전체 원문에서 예약 토큰을 지우면 저장 전 새 ID 생성과 기존 링크 영향 경고를 보여준다.
- 예약 메타 토큰과 미디어 토큰은 나무위키 동일 문법이 아니라 기존 링크·미디어를 지키기 위한 CWK 안전 확장이다.

## 8. 목표 사용자 흐름

### 8.1 방문자 읽기

1. 방문자는 기존 주소로 About 문서를 연다.
2. 제목 아래에서 최근 수정 시각과 현재 리비전을 본다.
3. 목차로 원하는 섹션에 이동한다.
4. `역사`에서 수정 기록과 편집 요약을 본다.
5. 두 리비전을 골라 차이를 비교한다.

### 8.2 OWNER 전체 편집

1. OWNER가 `편집`을 누른다.
2. 현재 리비전의 전체 원문을 불러온다.
3. 원문을 수정하고 `미리보기`로 결과를 본다.
4. 선택적으로 `저장 전 변경 비교`를 확인한다.
5. 편집 요약을 선택적으로 쓰고 저장한다. 섹션 이동 같은 시스템 동작에는 자동 요약이 붙는다.
6. 서버가 기준 리비전이 여전히 최신인지 검사한다.
7. 같으면 새 리비전을 생성하고 문서의 현재 리비전을 갱신한다.
8. 다르면 덮어쓰지 않고 최신본과 내 수정본의 충돌 화면을 보여준다.

### 8.3 OWNER 문단 편집

1. 섹션의 `[편집]`을 누른다.
2. 해당 제목과 본문 범위만 편집기에 보인다.
3. 저장 시 서버는 전체 원문에서 안정적인 섹션 ID를 기준으로 범위를 교체한다.
4. 섹션 제목을 바꿔도 기존 앵커 ID는 자동으로 유지된다.

### 8.4 되돌리기

1. OWNER가 역사에서 과거 리비전을 연다.
2. 현재본과 차이를 확인한다.
3. 되돌리기 사유를 입력하고 확인한다.
4. 필수 되돌리기 사유를 입력하면 선택한 과거 원문을 내용으로 하는 새 리비전이 만들어진다.

### 8.5 방문자 편집 요청(V1.1 선택 확장)

1. 방문자가 `편집 요청`을 누른다.
2. 현재 원문을 바탕으로 수정하고 요약을 쓴다.
3. 요청을 제출하면 직접 문서에 반영되지 않는다.
4. OWNER가 현재 리비전과 제안본의 diff를 검토한다.
5. 승인하면 최신 상태와 다시 충돌 검사 후 새 리비전으로 반영한다.
6. 거절·닫기 시 이유를 남긴다.

## 9. 개념 데이터 구조

구현 단계에서 컬렉션 이름은 조정할 수 있지만 책임은 분리한다.

### `wiki_documents`

- `slug`: `about`
- `title`
- `current_revision`
- `status`
- `created`, `updated`

### `wiki_revisions`

- `document`
- `revision_no`
- `source`: 나무마크 원문
- `summary`
- `actor_type`: owner, migration, edit_request
- `actor_id`: 공개 가능한 내부 식별자
- `base_revision`
- `source_hash`
- `title_snapshot`
- `profile_snapshot`
- `actor_label`: `OWNER`, `마이그레이션`, `편집 요청 반영` 등 공개용 표시
- `visibility`: public, suppressed
- `suppression_reason`: OWNER 비상 억제 사유
- `created`

제목, 프로필, 본문 중 하나라도 바뀌면 새 리비전을 만든다. 리비전 내용은 추가만 허용하고 일반 수정·삭제를 금지한다. 다만 연락처·비밀값 등 민감정보가 실수로 공개된 경우 OWNER가 해당 리비전 원문을 공개 화면에서 즉시 억제할 수 있다. 억제 사실·시간·사유는 감사 기록으로 남고 일반 방문자는 원문과 diff를 볼 수 없다.

### `wiki_edit_requests` — V1.1 선택 확장

- `document`
- `base_revision`
- `proposed_source`
- `summary`
- `status`: open, accepted, rejected, closed
- `reviewer`
- `review_note`
- `created`, `reviewed_at`

### 프로필 데이터

프로필 표는 일반 본문 문법에 묻지 않고 구조화 데이터로 유지한다. 왼쪽 사이드바와 About 표가 계속 같은 원천을 보게 한다. 프로필 행·사진·제목 수정도 새 리비전을 만들고, `profile_snapshot`에 당시 값을 남겨 과거 화면을 재현한다. 과거 스냅샷이 참조하는 media 원본은 물리 삭제하지 않고 공개 상태만 전환한다.

### 개인정보 원칙

- 공개 역사에 방문자 IP를 표시하지 않는다.
- OWNER 이름 외의 내부 계정 ID는 그대로 공개하지 않는다.
- V1.1 스팸 방지 정보가 필요하면 서버 내부에서만 최소한으로 보관하고 보존 기간을 둔다.

## 10. 저장과 충돌 처리

새 리비전 저장은 하나의 원자적 작업이어야 한다.

1. 클라이언트가 `base_revision`과 새 원문을 보낸다.
2. 서버가 현재 리비전과 `base_revision`을 비교한다.
3. 다르면 `409 Conflict`로 응답하고 아무것도 덮어쓰지 않는다.
4. 같으면 원문을 검증하고 해시를 만든다.
5. 다음 번호의 리비전을 추가한다.
6. 문서의 `current_revision`을 새 번호로 바꾼다.

PocketBase 클라이언트에서 리비전 생성과 현재 포인터 갱신을 두 번 호출하면 중간 실패와 경쟁 조건이 생긴다. 따라서 서버 hook, custom endpoint 또는 transaction을 쓰는 단일 서버 저장 경로를 V1 전제로 한다.

네트워크 재시도로 같은 저장이 두 번 생기지 않도록 요청 ID 또는 원문 해시를 이용한 중복 방지도 둔다.

### 10.1 운영 상한

- 기존 긴 About 저장 능력을 낮추지 않도록 원문 저장 한도는 최대 5,000,000자를 유지한다.
- 실제 공개 전에는 최대 크기 파싱 시간과 메모리를 측정하고, 긴 파싱이 UI를 멈추지 않게 처리한다.
- 브라우저 inline diff는 비교 원문 합계 400,000자까지 제공한다. 초과하면 변경량 요약과 원문 보기만 제공하고 서버 측 제한 diff를 사용한다.
- 역사 목록은 최신 50개씩 페이지를 나눈다.
- V1.1 익명 편집 요청은 원문 크기, 빈도, 동시 열린 요청 수를 별도로 제한한다.

## 11. 기존 문서 마이그레이션

마이그레이션 목표는 두 가지로 나눈다. 원본 JSON과 HTML 바이트는 체크섬과 함께 100% 보존하고, 새 공개 화면은 기존 문서의 의미·링크·미디어·배치를 시각 회귀로 보존한다.

1. 운영 `about_wiki_document` JSON과 관련 미디어를 먼저 백업한다.
2. 원본 JSON과 HTML의 체크섬을 기록한다.
3. 복사한 DB에서 HTML → V1 원문 변환기를 시험한다.
4. 자동 변환이 애매한 요소는 raw HTML로 공개 렌더링하지 않는다. 원본 백업에 그대로 보존하고, sanitizer를 거친 격리 미리보기와 수동 변환 목록으로 남긴다.
5. 변환 원문과 렌더링 결과를 현재 화면과 비교한다.
6. 확인된 결과를 `migration` 작성자의 리비전 1로 넣는다.
7. 기존 JSON은 즉시 삭제하지 않고 롤백 기간 동안 보존한다.
8. 공개 전환 후 문서, 프로필 표, 링크, 이미지, 모바일 화면을 확인한다.

프로필 표의 공유 데이터와 기존 미디어 원본은 마이그레이션 과정에서 분리하거나 삭제하지 않는다.

## 12. V1 인수 기준

### A. 읽기 화면

- 기존 `about.html` 주소와 기존 대표 앵커가 유지된다.
- 제목, 최근 수정, 프로필 표, 목차, 번호 섹션, Contact가 올바른 순서로 보인다.
- 목차 클릭 시 대응하는 제목으로 이동한다.
- 각주·표·접기·미디어가 원문과 동일한 의미로 렌더링된다.
- 비로그인 방문자에게 OWNER 편집 기능이 보이지 않는다.

### B. 편집

- OWNER는 전체 문서와 개별 문단을 원문으로 편집할 수 있다.
- 미리보기는 저장 후 공개 화면과 같은 렌더러를 쓴다.
- 일반 편집 요약은 선택 입력이고, 되돌리기 사유는 필수다.
- 저장 실패, 파서 오류, 충돌 때 원문이 사라지지 않는다.
- 열린 편집기에 저장되지 않은 내용이 있으면 자동 새로고침이 미뤄진다.
- 기존 media 선택·새 업로드·토큰 삽입을 원문 편집기에서 할 수 있다.

### C. 문법

- 지원 표에 포함된 각 문법의 정상·중첩·깨진 입력 테스트가 있다.
- 지원하지 않는 문법은 조용히 잘못 렌더링하지 않고 원문 또는 명확한 경고로 보존된다.
- 스크립트 삽입과 위험한 URL이 실행되지 않는다.

### D. 역사·diff·되돌리기

- 모든 정상 저장은 연속된 새 리비전을 한 개 만든다.
- 역사에 시간, 편집자 표시, 증감량, 요약이 보인다.
- 두 리비전의 추가·삭제·변경이 색상 외 표시와 함께 구분된다.
- 되돌리기는 과거 기록을 지우지 않고 새 리비전을 만든다.
- 동시 편집 시 나중 저장이 앞선 저장을 덮어쓰지 않는다.
- OWNER는 민감정보가 든 리비전을 공개 역사·원문·diff에서 비상 억제할 수 있고 감사 사유는 남는다.

### E. 편집 요청 — V1.1 구현 시 적용

- 방문자는 직접 문서를 변경할 수 없다.
- 요청에는 기준 리비전, 제안 원문, 요약이 기록된다.
- OWNER는 diff를 본 뒤 승인·거절·닫기할 수 있다.
- 오래된 기준 리비전의 요청은 승인 전 충돌을 알려준다.
- 공개 화면에 방문자 IP가 노출되지 않는다.

### F. 권한

- 공개 읽기와 역사 조회는 로그인 없이 가능하다.
- OWNER만 직접 저장·되돌리기가 가능하고, V1.1에서는 요청 검토도 OWNER만 가능하다.
- 일반 PocketBase 로그인만으로 OWNER 권한을 얻을 수 없다.
- 서버 API에서도 같은 권한을 검사해 UI 숨김만으로 보호하지 않는다.

### G. 모바일·접근성

- 320, 375, 390, 640, 768px에서 콘텐츠 경계를 측정했을 때 페이지 전체 가로 스크롤이나 잘림이 생기지 않는다. `overflow-x: hidden`으로 문제를 감춘 상태는 통과로 보지 않는다.
- 넓은 표와 코드만 자체 컨테이너 안에서 가로 스크롤된다.
- 모바일 편집 도구의 hit area는 최소 44px을 목표로 하되 데스크톱의 작은 레트로 링크 시각 크기는 유지한다.
- 제목 계층과 표 머리글이 의미에 맞는 HTML로 출력된다.
- 키보드만으로 목차, 접기, 편집, 역사, diff를 사용할 수 있다.
- 포커스 표시가 보이며 diff는 빨강·초록 색상만으로 의미를 전달하지 않는다.
- 화면 읽기 프로그램용 버튼 이름과 상태가 제공된다.

### H. 라우팅·SPA 회귀

- 읽기, 편집, 역사, 리비전 원문, diff는 각각 복사 가능한 직접 URL을 가진다.
- 직접 주소 진입, 새로고침, 브라우저 뒤로·앞으로 이동이 같은 상태를 복원한다.
- 사이트 내부 SPA형 본문 교체 후에도 중복 이벤트 없이 위키 화면이 한 번만 초기화된다.
- 편집 중 내부 이동에는 미저장 내용 경고가 나오며 취소하면 원문이 유지된다.

## 13. 구현 순서 제안

### 2단계: 기반

- 개념 스키마를 실제 PocketBase 컬렉션과 권한 규칙으로 확정
- V1 문법 파서·안전 렌더러
- fixture 기반 문법·보안 테스트

### 3단계: OWNER 편집과 이력

- 읽기 화면과 원문 편집기 연결
- 미리보기·편집 요약·저장
- 역사·diff·되돌리기
- 충돌 처리

### 4단계: 마이그레이션과 공개 전환

- 운영 데이터 백업
- 복사 DB 마이그레이션 리허설
- 현재 화면과 렌더링 비교
- 모바일·접근성·OWNER 실제 저장 검증
- 배포와 롤백 확인

### 5단계: 방문자 편집 요청(V1.1 선택 확장)

- 요청 제출·검토·승인 흐름
- 스팸 방지와 개인정보 보존 정책
- 운영 후 필요성이 확인된 경우에만 공개

## 14. 결정된 사항과 남은 판단

### 이번 단계에서 결정

- V1은 나무마크 전체가 아니라 명시된 핵심 부분집합을 지원한다.
- About과 Contact는 한 문서를 유지한다.
- URL은 `about.html`을 유지한다.
- OWNER만 직접 편집하고 방문자 기여를 열 경우에도 V1.1 편집 요청만 허용한다.
- 프로필 표는 구조화 데이터로 유지하고 사이드바와 공유한다.
- 본문 원문과 리비전이 새로운 기준 데이터가 된다.
- 공개 역사에 방문자 IP를 노출하지 않는다.
- 저장 전 diff는 우리 사이트의 추가 안전 기능으로 분류한다.

### 구현 전에 기술 검증할 사항

- V1 파서를 직접 작게 만들지, 호환 가능한 기존 파서를 제한적으로 쓸지
- PocketBase에서 리비전 생성과 현재 포인터 갱신을 원자적으로 묶는 정확한 방식
- 현재 HTML 중 자동 변환이 어려운 요소의 실제 목록
- 프로필 스냅샷을 리비전에 포함할 때의 저장 형태

이 네 가지는 제품 방향을 다시 묻는 선택지가 아니라, 2단계 초반에 코드·데이터를 확인해 결정할 구현 세부 사항이다.

## 15. 완료 정의

1단계는 다음 조건으로 완료한다.

- 현재 작동 방식과 목표 작동 방식이 구분되어 있다.
- 나무위키에서 가져올 것과 제외할 것이 명시되어 있다.
- V1 문법 범위가 고정되어 있다.
- V1의 읽기·편집·역사·권한·모바일 인수 기준과 V1.1 편집 요청 인수 기준이 구분되어 있다.
- 데이터 구조, 충돌 처리, 안전한 마이그레이션 원칙이 정의되어 있다.
- 다음 단계가 제품 방향 추가 질문 없이 기술 검증부터 시작할 수 있다.
