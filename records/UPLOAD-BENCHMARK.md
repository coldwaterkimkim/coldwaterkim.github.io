# 기존 작성기 / Records V2 업로드 비교 · 2026-09-05

## 결론

사진 3장 첨부 완료 표시는 V2가 약 82ms 빨랐다. 16MiB/96MiB 영상의 중앙값 차이는 각각 +7ms/+30ms였다. 300MiB는 작성기가 열린 직후 시작한 본측정에서 V2가 약 368ms(+8.9%) 느렸으나, 양쪽에 동일하게 1.5초 화면 안정화 시간을 준 추가 측정에서는 기존 3.888초 / V2 3.868초였다. 이번 표본만으로 지속적인 대용량 업로드 성능 저하 또는 동등성을 통계적으로 확정하지 않는다.

전송 엔진은 변경하지 않았다. `js/pb.js`, `js/editor-upload-coordinator.mjs`, `js/markdown-editor.js`는 main과 diff가 없다. 근거가 부족한 병렬 수 조정이나 배너 제거도 하지 않았다.

## 환경과 방법

- 비교 대상: 기존 `/admin/daily.html?new=1`의 BlockNote 작성기, V2 `/records/#compose`. 동일 worktree `1c69877`.
- Chrome 152, macOS, 1200×1284 viewport. 최초 Chrome 도구 연결이 끊겨 별도의 작업 전용 Chrome CLI 세션으로 실측했다. 개인 계정 탭은 사용하지 않았다.
- Vite 127.0.0.1:5196 → 별도 PocketBase 127.0.0.1:18096. 운영 DB/미디어에 쓰지 않았다. 네트워크 속도 제한 없는 loopback 전송이다.
- UI의 실제 file input에 같은 디스크 파일을 선택했다. API 함수를 직접 호출하여 작성기를 우회하지 않았다. 글 저장/게시는 실행하지 않았다.
- 매회 전체 reload. A/B 준비 측정 각 1회 제외 후 A-B-B-A / B-A-A-B, 각 작성기 4회. 파일 이름과 내용 동일, 순차 실행. 캐시 재사용으로 네트워크가 없는 예비 측정은 `exploratory/`에 분리하고 결과에서 제외했다.
- 사진: 3000×2000 합성 노이즈 JPEG 3개, 각 약 4MiB. 영상: 유효한 3초 H.264 MP4에 `free` atom을 덧붙여 정확히 16/96/300MiB로 만든 전송 시험 파일. 300MiB 파일의 전체 디코딩도 확인했다. 긴 실제 영상이나 압축/변환 성능 표본은 아니다.
- BGM 정지. 로컬 영상 변환 worker는 실행하지 않았다. 진단 옵션을 양쪽 동일하게 켰으며, 대용량 경로에 기본 동작에는 없는 8MiB 원본 읽기 계측이 포함된다.
- 16MiB/사진은 직접 POST, 96MiB는 tus 3개 병렬, 300MiB는 서버 설정에 따른 tus 6개 병렬. chunk32MiB. 병렬 설정을 강제하지 않았다.

| 96MiB | 서버 미디어 등록 | 0.643초 | 0.615초 |
| 300MiB | 실제 PATCH 전송 | 1.499초 | 1.778초 |
| 300MiB | 서버 미디어 등록 | 1.487초 | 1.550초 |

전체 시간에는 파일 준비, 재개 상태 확인, tus 생성/분할 결합, 화면 반영도 포함된다. 직접 POST 경로는 전송과 서버 저장이 하나의 요청이므로 순수 전송 시간으로 분리하지 않았다. 서버 미디어 등록은 영상 변환/파생본 생성을 뜻하지 않는다.

## 300MiB 추가 확인

모든 조건에서 작성기를 띄운 뒤 1.5초 기다렸다. 기존 2회, V2 정상 움직임 3회, V2 CSS animation/transition 일시 중지 3회를 교차 실행했다.

| 조건 | 중앙값 |
|---|---:|
| 기존 | 3.888초 |
| V2 정상 움직임 | 3.868초 |
| V2 CSS 움직임 일시 중지 | 3.797초 |

처음 관측한 +8.9% 차이는 이 조건에서 재현되지 않았다. CSS 움직임 중지의 약 71ms 차이만으로 마키/블링크가 원인이라고 확정하지 않았다. native marquee를 포함한 모든 움직임의 정지를 별도로 증명한 실험도 아니다. 제품 코드에는 움직임 중지를 적용하지 않았다.

## 무결성, 표시와 정리

- 본측정 40회 + 추가 조건 8회 + 사진 표시 확인 2회 = 50회, 첨부 74개 전부 원본 다운로드 SHA-256 일치. 별도 예비/중단 회차의 시험 첨부도 원본 대조 후 정리했다.
- 모든 본측정/추가 대용량 회차의 diagnostic 1개, outcome complete, 실제 accepted PATCH bytes = 파일 크기 확인. 성공 기록/타이밍/체크섬 로그 누락 없음.
- 지난 회차 정리된 tus 주소에 대한 HEAD 404는 재개 가능 여부 확인 후 새 전송을 시작한 결과다. PATCH는 모두 204이며 부분 재개/전송 생략은 없었다. 이를 업로드 실패로 세지 않았다.
- 사진 표시 별도 확인: 양쪽 3개 이미지 모두 complete + naturalWidth>0. 기존은 800px 썸네일, V2는 3000px 원본을 표시했다. 표시용 이미지 다운로드 비용은 운영 회선에서 별도 관찰할 항목이다.
- 시험 첨부는 정확한 생성 ID만 DELETE 204로 정리. 검증 종료 시 시험 시간 이후 생성된 로컬 media 0개, 이번 런타임 `tus/`의 잔여 파일 0개.
- 운영 배포/병합 없음. 실제 인터넷 회선, 실물 모바일, 다중 업로드 경쟁, 장시간 영상 변환까지 같은 속도라고 보장하는 결과는 아니다.
